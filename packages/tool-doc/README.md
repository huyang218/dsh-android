# dsh-plugin-tool-doc

给无 shell 的 agent 一个 `read_document`:读 `.docx` / `.xlsx` / `.pptx`。

## 为什么非要一个工具

`tool-fs` 的 `read` 是**文本**读取器。指给它一个 `.docx`,它不会报错——它会把 ZIP 的字节
当文本吐出来,然后模型拿着那堆噪声推理。手机上人常留的恰好就是这类文件,所以这是
"文件系统 + LLM + 会话 + 附件"这句话缺的那一半。

砍掉 shell 之后也没有退路:没有 `pdftotext`,没有 `unzip`,没有任何管道。

## 零依赖,种子不用动

docx/xlsx/pptx 本质是 **ZIP + XML**,而 Node 自带 `zlib`。所以这个包:

- `lib/zip.js` —— 最小 ZIP 读取器(中央目录 + store/deflate),约 120 行
- `lib/ooxml.js` —— 从标签流里按文档顺序抽文本,不建 DOM
- `lib/extract.js` —— 按**魔数**分派,不信扩展名
- `lib/index.js` —— cordis 插件,注册 `read_document`

代价说清楚:**这不是转换器**,答不了"哪个单元格合并了""这段是不是粗体"。它是模型开始
推理之前那一步——"这份文件到底写了什么"。

不加依赖的好处不只是省事:`vendor/seed` 的锁不用重生成,已经 258MB 的载荷不再变大,
公开 apk 里也不多一份 licence。

## 几个不显眼但会出错的地方

- **XML 实体里 `&amp;` 必须最后解**。先解会把编码过的 `&amp;lt;` 变成真的 `<`。
- **docx 的制表符和换行在 `<w:t>` 外面**。只抽 `<w:t>` 会把两列表格压成一行。
- **xlsx 的 `t="s"` 是 sharedStrings 的下标**。忽略共享串表会得到一张全是整数的表——
  看着像数据,其实全错。空的 `<si/>` 也必须占位,否则后面每个下标都错位。
- **空单元格写作 `<c r="B1"/>`**。只认 `<c …>…</c>` 的正则不是"跳过它",而是把它当开
  标签、一路吃到**下一个**单元格的 `</c>`——两列并成一列,后面每一列都平移,而这一行
  看上去仍然像正常数据。这条有回归测试。

## PDF:明确不做

不是漏了。PDF 抽文本要走 xref、解流、切 content stream、再按每个字体的 ToUnicode CMap
映射字符——**最后一步错了不会报错,只会给出看起来合理的错字符**。两条路代价都不小:

- 手搓:几百行,而且对子集内嵌 CID 字体基本无解;
- `pdfjs-dist`:约 10MB 进种子,而种子已经 258MB 且要塞进公开 apk。

所以留着不做,而不是做一半。`read_document` 见到 `%PDF-` 会**指名报出来**,不会把二进
制当文本喂给模型。要做哪条,是个待定的决定,不是待办的活。

## 实测(2026-08-23,Android 15 / API 35 模拟器)

真的 docx / xlsx 推进工作区,让 agent 自己读:

- 模型自行调用 `read_document` 两次(并行),docx 拿到"季度报告 / 营收 1200 万 /
  结论:同比增长 18%",xlsx 拿到 `## 销售` 加制表符分隔的行,共享串正常解析。
- 故意在 B3 埋的空单元格体现为多出来的那个制表符——上面第四条的正向证据。
- `notes.pdf`:模型直接说不支持并给了替代路径,没有去啃二进制。
